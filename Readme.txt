2. 프로그램 개요 및 구성
----------------------------------------------------------------

  2.1 시스템 개요

  AWS의 Master 1개와 로컬 PC의 Worker 4개로 구성한 분산 저장 시스템.
  각 Worker는 독립적인 Thread, 대기 큐, 저장소를 사용하며,
  Master-Worker 및 Worker-Worker 간 통신에는 TCP 소켓 사용.

  Master에서 고유한 4자리 16진수 Key와 1~100 정수 Value 5,000쌍 생성.
  Worker에 작업을 분배하고, 실패한 작업은 다른 Worker에 재할당.
  특정 Worker에 작업이 집중되면 P2P 통신으로 대기 작업 이전.

  - 작업 처리: 매 시도 가상 1~3초, 성공 확률 80%·실패 확률 20%
  - 대기 큐: 처리 중 작업을 제외하고 최대 10개, 초과 요청은 FAIL 기록
  - 큐 경고: 입출력 전후 큐 크기 중 하나라도 8개 이상이면 WARN 기록


  2.2 소스 파일 구성

  master.py
    작업 생성·분배·재할당, 전역 시계, 작업 소유권 및 전체 결과 관리

  worker.py
    Worker별 큐·저장소·통계 관리, 작업 처리 및 P2P 연동

  run_workers.py
    Worker 4개를 독립 Thread로 실행하고 종료 관리

  p2p.py
    이웃 큐 조회, Worker 간 직접 전송 및 수신 상태 확인

  protocol.py
    줄바꿈으로 구분한 JSON 메시지의 TCP 송수신

  logger.py
    노드별 로그 기록 및 이벤트 명세 파일 AllDefinedLogs.txt 생성


3. 컴파일 및 실행 방법
----------------------------------------------------------------

  3.1 실행 환경

  사용 언어 : Python 3.10 이상
  Master 환경 : AWS EC2 / Ubuntu / Python 3.14.4
  Worker 환경 : Windows / Python 3.12.14
  외부 패키지 : 없음 (Python 표준 라이브러리만 사용)
  Master 주소 : 52.79.236.152
  Master 포트 : TCP 5000
  Worker P2P 주소 : 127.0.0.1, TCP 6001~6004

  Master는 AWS 서버에서, Worker 4개는 한 대의 로컬 Windows PC에서 실행.
  아래 명령 중 [AWS]는 SSH로 접속한 Ubuntu 터미널에서,
  [Windows]는 로컬 PC의 PowerShell에서 실행.


  3.2 실행 준비

  (1) 제출 압축 파일을 해제하고 아래 소스 파일 6개가 같은 폴더에
      있는지 확인. 파일 이름과 확장자는 그대로 유지.

      master.py       worker.py       run_workers.py
      p2p.py          protocol.py     logger.py

  (2) 로컬 PC에서 소스 파일 6개가 있는 폴더를 열고 PowerShell 실행.

      Python 3.10 이상과 소스 파일 6개가 표시되는지 확인.
      python 명령이 없고 py --version이 정상 동작하는 경우,
      이후 Windows 명령의 python을 py로 변경하여 실행 가능.
      둘 다 없다면 Python 설치 후 PowerShell을 다시 열어 진행.

  (3) AWS 서버에 SSH 접속 후 소스 폴더로 이동.
      아래 개인키 경로는 접속 권한이 있는 키 파일의 실제 위치로 변경.
      개인키는 소스 코드 및 제출 압축 파일에 포함하지 않음.

      [Windows - AWS 접속]
      ssh -i "C:\키저장폴더\video_0921.pem" ubuntu@52.79.236.152

      [AWS - 접속 후]
      cd ~/dc1/test_0921/final-v2
      ls *.py
      python3 --version

      위 서버 경로에는 실행용 소스가 배치되어 있음.
      별도 서버에서 재현할 때는 동일한 소스 6개를 서버의 한 폴더에
      배치한 뒤 그 폴더에서 실행. Worker의 접속 주소도 해당 서버로 변경.

  네트워크 조건
  - 현재 AWS는 SSH TCP 22 및 작업 통신 TCP 5000 접속 허용 상태.
  - 별도 서버 사용 시 위 포트의 접속 허용 필요.
  - Worker 4개는 같은 PC에서 실행하므로 P2P 주소는 127.0.0.1 사용.
  - 로컬 6001~6004 포트는 다른 프로그램이나 중복 실행과 충돌하지 않아야 함.


  3.3 소스코드 컴파일 및 문법 검사

  이 프로그램은 Python 소스를 인터프리터로 실행하는 방식이며,
  C·Java처럼 별도의 실행 파일을 만드는 빌드 과정은 필요하지 않음.
  Python은 실행 과정에서 소스를 바이트코드로 컴파일하여 처리.

  실행 전에 py_compile 명령으로 소스 6개를 바이트코드로 컴파일하여
  문법 오류를 확인할 수 있음. 각 환경의 소스 폴더에서 아래 명령 실행.

  [AWS]
  python3 -m py_compile master.py worker.py run_workers.py p2p.py protocol.py logger.py

  [Windows]
  python -m py_compile master.py worker.py run_workers.py p2p.py protocol.py logger.py

  확인 방법
  - 오류 메시지 없이 명령 입력줄이 다시 나타나면 컴파일 검사 통과.
  - 생성되는 __pycache__ 폴더는 바이트코드 캐시이며 별도 실행 대상이 아님.
  - SyntaxError 등의 오류가 표시되면 파일명·줄 번호 확인 후 해결 필요.
  - 이 검사는 문법 검사이므로 소켓 연결과 실제 처리까지 보장하지 않음.
  - 아래 Master·Worker 실행 및 종료 확인까지 진행해야 동작 확인 완료.


  3.4 Master 실행 - AWS에서 먼저 실행

  AWS 터미널의 소스 폴더에서 다음 명령을 한 줄로 입력.

  python3 -B master.py --host 0.0.0.0 --port 5000 --count 5000 --seed 17 --log-dir logs/master

  옵션 설명
  - -B          : 실행 중 바이트코드 캐시 파일 생성을 생략
  - --host      : 연결을 받을 주소. 0.0.0.0은 서버의 모든 IPv4 인터페이스 사용
  - --port      : Worker 연결을 받을 포트, 5000
  - --count     : 생성할 작업 수, 5,000개
  - --seed      : 난수 생성 기준값, 17
  - --log-dir   : 현재 소스 폴더 기준 Master 로그 저장 경로

  다음 문구가 표시되면 Master가 연결을 기다리는 상태.

    - Master 0.0.0.0:5000 연결 대기

  AWS 창을 유지한 채 바로 다음 단계의 Worker 실행 진행.
  연결 대기 제한이 60초이므로 로컬 실행 명령도 미리 준비.
  제한시간 초과로 종료된 경우 Master부터 다시 시작.


  3.5 Worker 실행 - 로컬 Windows에서 실행

  AWS에 접속한 창과 별도로 로컬 PowerShell을 열고,
  run_workers.py가 있는 소스 폴더에서 다음 명령을 한 줄로 입력.

  python -B run_workers.py --master-host 52.79.236.152 --master-port 5000 --peer-host 127.0.0.1 --peer-base-port 6000 --seed 10 --timeout 60 --log-dir logs/workers

  옵션 설명
  - --master-host    : AWS Master의 공인 IP. 0.0.0.0을 입력하지 않음
  - --master-port    : Master에서 지정한 포트, 5000
  - --peer-host      : Worker끼리 연결할 주소, 같은 PC이므로 127.0.0.1
  - --peer-base-port : 기준값 6000에 Worker ID를 더해 6001~6004 사용
  - --seed           : Worker별 난수 기준값. 10에 각 Worker ID를 더해 사용
  - --timeout        : Master 통신 대기 제한시간 60초. P2P 통신은 최대 5초.
  - --log-dir        : 현재 소스 폴더 기준 Worker 로그 저장 경로

  한 번 실행하면 Worker 4개가 각각 독립 Thread로 시작.
  worker.py를 직접 실행하거나 run_workers.py를 네 번 실행할 필요 없음.
  시작 시 표시되는 Worker 주소는 접속 설정 안내이며, 연결 성공 표시는 아님.
  Master가 Worker 4개의 준비 완료를 확인하면 자동으로 작업 분배 시작.

  상세 이벤트는 로그 파일에 기록되므로 터미널에 출력이 계속되지 않아도 정상.
  가상 처리시간 1~3초는 실제 대기시간이 아니며 --timeout과도 별개.


  3.6 진행 상황 및 정상 종료 확인

  실행 중 로그를 보려면 별도로 AWS에 SSH 접속한 터미널에서 실행.

  [AWS - 로그 보기]
  tail -n 10 -F ~/dc1/test_0921/final-v2/logs/master/Master.txt

  Master 실행 창은 유지하고, 로그 보기만 끝낼 때 해당 창에서 Ctrl+C 입력.
  전체 작업이 완료되면 별도 종료 명령 없이 Master와 Worker가 자동 종료.

  정상 종료 기준
  - 로컬 터미널에 아래 문구 출력.
    Worker1, Worker2, Worker3, Worker4가 모두 정상 종료했습니다.
  - Master.txt에 STOP | SUCCESS | 정상 종료 기록.
  - Master.txt의 전체 STAT에서 success가 5000인지 확인.

  [AWS - 종료 후 결과 확인]
  cd ~/dc1/test_0921/final-v2
  tail -n 6 logs/master/Master.txt

  Worker별 통계 4개, 전체 통계, 정상 종료 기록 확인 가능.
  오류로 중단된 경우에도 명령 입력줄은 돌아오므로 종료 로그까지 확인 필요.

  결과 파일 위치
  - AWS: logs/master/Master.txt
    전체 KV 5,000쌍, 작업 분배 및 Worker별·전체 통계
  - 로컬: logs/workers/Worker1.txt ~ Worker4.txt
    Worker별 처리·P2P 이전·최종 통계
  - 각 로그 폴더: AllDefinedLogs.txt
    프로그램에서 사용하는 로그 이벤트 명세

  노드별 결과는 AWS의 Master.txt와 같은 실행의 로컬 Worker 로그 4개 사용.
  로컬 로그 폴더에 초기화 과정으로 생성된 빈 Master.txt는 결과에서 제외.
  같은 --log-dir로 재실행하면 기존 로그가 초기화되므로 보존할 때는 경로 변경.


  3.7 실행 오류 확인

  파일을 찾을 수 없음
    현재 위치에 소스 6개가 있는지 확인하고 해당 폴더로 이동.

  ModuleNotFoundError: worker / p2p / protocol / logger
    소스 파일 누락·이름 변경·폴더 분리 여부 확인. 외부 패키지 설치 대상이 아님.

  Connection refused / 연결 거부
    Master가 실행 중인지, --master-host와 --master-port가 맞는지 확인.

  Connection timed out / 시간 초과
    네트워크 연결 및 서버 접속 허용 상태 확인.
    Master만 실행한 채 60초가 지났다면 Master부터 다시 실행.

  Address already in use / 주소 사용 중
    이전 Master·Worker 실행이 종료됐는지, 같은 포트를 중복 사용 중인지 확인.


4. 동적 작업 분배 알고리즘
----------------------------------------------------------------

  4.1 알고리즘 및 처리 순서

  -> "최소 부하 우선 분배 + 동률 시 순환 선택"

  판단 부하 = 보고된 대기 큐 크기 + 큐 반영 확인 전 배정 작업 수

  ① 실패 재시도 작업을 새 작업보다 먼저 선택.
  ② 부하가 10 미만인 Worker 중 최소 부하 선택.
     실패 재시도에서는 직전에 실패한 Worker 제외.
  ③ 동률이면 마지막 배정 위치의 다음 Worker부터 순환 선택.
  ④ 수락·큐 반영 확인까지 배정 상태 유지.
     모든 후보에 여유가 없으면 큐 상태 갱신 대기.
  ⑤ P2P 점검 중 신규 작업 배정·실패 작업 재배정은 잠시 보류.
     기존 작업 처리와 응답 수신은 계속 진행.
     진행 중인 점검이 모두 끝나면 배정 재개 후 다음 점검 진행.

  Worker 내부에서도 예약되지 않은 실패 재시도 작업을 우선 처리.
  같은 종류의 작업끼리는 FIFO 순서 유지.


  4.2 장점과 단점

  장점
  - 큐 상태 변화와 전송 중 작업을 고려하여 과도한 배정 감소.
  - 동률 시 순환 선택으로 특정 Worker에 작업이 집중되는 현상 완화.

  단점
  - Master에 분배 부담이 집중되고 큐 보고에 시차 발생 가능.
  - 작업별 처리시간을 예측하지 않으며, 실패가 많으면 일반 작업 지연.
  - P2P 점검 중에는 새 배정이 지연될 수 있음.


5. P2P 부하 분산 알고리즘
----------------------------------------------------------------

  5.1 점검 및 대상 선택

  임계값 기반 최소 큐 선택 + 큐 차이 절반 이전

  예상 대기시간 = 대기 작업 수 × 평균 처리시간 2초

  예상 대기시간이 15초를 초과하는 경우, 즉 대기 작업 8개 이상일 때 이전 시도.
  Master가 전역 가상 시간 기준 1~3초 랜덤 주기로 Worker별 점검을 대행.
  Worker는 실제 큐를 재확인한 뒤 다른 Worker의 큐를 직접 조회.
  진행 중인 점검이 끝날 때까지 추가 점검 요청은 보류하며, 주기별 판단은 유지.

  응답한 Worker 중 최소 큐 선택. 동률이면 Worker ID가 작은 쪽 우선.

  이전 개수 = min((송신 큐 - 수신 큐) // 2, 수신 큐의 남은 공간)

  예약 직전 송신 큐를 재확인해 이전 개수를 조정하며,
  큐 뒤쪽에서 예약 가능한 작업만 선택. 수신 측에서도 공간 재확인.
  계산한 개수는 예약 가능한 작업 수와 수신 측 실제 여유에 따라 줄거나 거절될 수 있음.


  5.2 이전 순서

  ① 송신 작업 예약 및 송신 시각 확정
  ② Worker 간 TCP 소켓으로 작업 직접 전송
  ③ 수신 공간·시각 확인 후 수신 큐에 예약 상태로 추가
  ④ 수신 확인(ACK) 후 송신 큐에서 작업 제거
  ⑤ Master가 소유권을 확정하면 수신 예약 해제 및 처리 가능

  Key·Value·시도 번호는 이전 전후 동일하게 유지.
  큐 차이가 작거나 수신 공간이 부족하면 이전하지 않을 수 있음.


  5.3 장점과 단점

  장점
  - 작업 데이터를 Master를 거치지 않고 직접 전달하여 부하 분산.
  - 예약·ACK로 중복 처리를 막고, 수신 공간 확인으로 큐 초과 방지.

  단점
  - 큐 조회·시각 확인·ACK에 추가 통신 비용 발생.
  - 조회 후 부하 변화나 동일 대상에 대한 동시 요청으로 이전 거절 가능.


6. 장애 처리 메커니즘
----------------------------------------------------------------

  작업 처리 실패
    Master가 실패 작업을 재시도 우선 큐에 등록하고 다른 Worker에 재할당.
    재시도에도 성공 80%·실패 20%를 적용하며 성공할 때까지 반복.

  큐 초과 및 P2P 수신 거절
    큐 초과 거절은 확률에 따른 처리 실패와 별개로 취급.
    일반 배정은 여유에 따라 재시도하며, P2P 수신 거절이 확정되면
    송신 예약을 해제하여 일반 처리로 복귀.

  ACK 미수신
    이전 ID로 수신 상태 조회. 수신 완료면 이전 확정, 거절이면 예약 해제.
    3회 조회 후에도 UNKNOWN이면 예약을 유지하고 P2P_FAILURE 보고 후
    전체 실행을 실패 종료하여 중복 처리·유실 여부를 임의로 판단하지 않음.

  중복 및 연결 장애
    메시지·작업 시도·이전 ID를 이용해 중복 처리와 중복 집계 방지.
    복구할 수 없는 연결 장애는 오류 기록 후 종료.
    Worker 자동 재접속 및 디스크 기반 작업 복원 기능은 미구현.


7. 가상 시간 및 통계
----------------------------------------------------------------

  7.1 시간 계산

  Master의 시계를 0에서 시작해 처리 시도마다 1~3초,
  메시지 편도 전송마다 1초 누적. 병렬 Worker의 비용도 전역 시계에 합산.
  P2P 통신은 메시지 ID로 중복 비용을 제외하고 종료 통신까지 반영.
  실제 sleep으로 기다리지 않으므로 가상 수행시간과 실제 실행시간은 서로 다름.

  평균 대기시간 = 큐에서 처리 시작까지 기다린 시간 합계 / 처리 시작 횟수

  P2P 이전 전후의 대기는 합산하되 이동 구간은 제외.
  실패 후 재할당은 새로운 처리 시도로 계산.


  7.2 기록 통계

  ① Worker별 처리량   : 성공적으로 저장한 KV 수
  ② 성공·실패 횟수    : 실제 처리 시도의 성공 및 실패 수
  ③ 평균 대기시간    : 성공·실패 시도를 포함한 큐 대기시간 평균
  ④ P2P 이벤트 횟수  : 성공한 고유 이전 ID 수
  ⑤ 장애 재할당 횟수 : 실패 후 다른 Worker에 재배정된 횟수
  ⑥ 전체 수행시간    : 종료 통신까지 포함한 최종 가상 시간

  여러 작업을 한 번에 옮겨도 P2P 이벤트는 1회로 집계.
  송신·수신 Worker에는 각각 1회 기록하므로 Worker별 합계는 전체의 2배.
  작업 완료 및 진행 중 이전 정리 후 STOP/STOP_ACK로 통계 확인.
  FINAL_STATS 4건의 비용까지 반영한 공통 최종 시각을 기록하고 종료.


8. 추가 구현 및 실행 결과
----------------------------------------------------------------

  8.1 추가 구현

  - 분할·병합되어 도착한 TCP 데이터를 줄바꿈 기준 JSON 메시지로 구분.
  - 큐 버전으로 오래된 상태 보고를 구분하고 공유 데이터는 잠금으로 보호.
  - P2P 이전 작업별 ID·Key·시각을 기록하여 송수신 내역 대조 지원.


  8.2 실행 시험 결과

  AWS Master와 로컬 Worker 4개를 연결한 실행 시험 결과.

  성공한 고유 작업   : 5,000개
  처리 실패          : 1,244회
  장애 재할당        : 1,244회
  P2P 이전           : 67회 / 작업 77개
  작업 완료 시각     : 66,183초
  전체 가상 수행시간 : 66,195초
  평균 대기시간      : 약 342.788초

  생성 원본과 저장 결과 일치, 성공 작업의 중복·누락 없음 확인.
  로그의 큐 제한·통신비·대기시간·통계 대조 및 정상 종료 확인.
  별도 로컬 시험에서 중복 전송, ACK 유실 복구,
  UNKNOWN 3회 후 실패 종료 확인.

  난수 기준값이 같아도 스레드와 네트워크 처리 순서에 따라
  실행별 이전 횟수와 통계는 달라질 수 있음.
